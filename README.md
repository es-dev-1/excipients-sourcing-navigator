# Excipient Sourcing Navigator

An interactive tool to help pharma and nutra formulators find fitting excipient suppliers, organized by route of administration, functional category, and excipient type.

## Status
Active -- kickoff 2026-05-30

## Goal
Build a web-based tool that allows users to navigate the excipient landscape by route of administration > category > excipient > supplier and quickly identify relevant suppliers for their formulation needs.

## Quick context
A single-page web tool (`index.html` plus two JSON data files) that lets PharmaExcipients.com visitors navigate the excipient landscape by route of administration > category > excipient > supplier > product. It builds on the pharma-excipients-landscape structure tree.

## Stages
1. Landing
2. Route of administration (7: Oral, Injectable, Inhalation / Pulmonary, Nasal, Topical, Ocular, Rectal & Vaginal)
3. Functional category
4. Excipient
5. Supplier (with a link to the supplier's PharmaExcipients.com page)
6. Products for that excipient + supplier (linked to the shop where a match exists)

## Data files and how to regenerate
Both JSON files are generated by `build-data.py` from the source files in `ea-work/data-for-reoccurring-tasks/`. To rebuild after any source update, run `python3 build-data.py` from this folder.

Three sources drive the whole tool:

| File | Drives | What it provides |
|------|--------|------------------|
| `excipients-landscape-structure-v2.md` | Stages 2-4 | Route (`#`) > category (`##`) > excipient (`- `) |
| `excipient-products-tree.md` | Stages 5-6 | Excipient (`##`) > supplier (`###`) > products, with e-shop links already resolved |
| `supplier-page-urls.md` | Stage 5 | Each supplier's PharmaExcipients.com page link |

- `excipients.json` (stages 2-5): route > category > excipient > suppliers, each supplier carrying its portal page link. Suppliers are read from the product tree, so an excipient's supplier list is whoever actually has a product filed under it.
- `products.json` (stage 6): excipient > supplier > products (name, chemical, involvement tag, function, shop links). Keyed by excipient *and* supplier, so no matching logic runs in the browser.

## Search

A search bar sits between the breadcrumb and the stage title on every stage, the landing page included. It only skips the user forward to a point in the tree. From there they browse on manually exactly as before, so nothing else about the flow changes.

Every route, every functional category, and every excipient is its own searchable node, built from `excipients.json` when the page loads: 7 route nodes, 77 category nodes, and 690 excipient nodes, 774 in total. Nothing is deduplicated, which is the whole point:

- Microcrystalline Cellulose (MCC) sits in four Oral categories and one Nasal one, so it is five separate hits, each landing on a different supplier list.
- Gelling Agents (In Situ) exists under both Nasal and Ocular, so it is two hits.

A hit never reaches past its own stage. A category hit reads `Nasal › Gelling Agents (In Situ)` and stops there; it does not name the excipients inside it. Picking a hit is identical to having clicked through to it by hand: a route opens its category list, a category opens its excipient list, and an excipient opens its supplier list.

Ranking, best first: the query starts the node's own name, starts a word inside it, appears anywhere in it, or matched only the route or category above it. Ties break by node type (route, then category, then excipient), then shorter name, then the taxonomy's own order, so Oral leads the way it does everywhere else.

Other behavior worth knowing: two characters minimum, every whitespace-separated word has to match, accents are folded, and 24 hits are shown with a count of the rest. Arrow keys and Enter work, Escape and the × clear the box, and `/` focuses it from anywhere on the page. Suppliers and products are deliberately not searchable: stages 5 and 6 depend on the excipient the user picked, so there is no single place a supplier hit could jump to.

No build step is involved. Anything added to the source structure file is searchable as soon as `build-data.py` has been run.

## Header mark

`assets/navigator-mark.webp` sits to the right of the tool name in the header. The header is sticky and lives outside `#app`, which is the only element re-rendered between stages, so the mark is on screen in all six stages without any per-stage logic.

It is generated by the same script from `Excipients Sourcing Navigator.jpg`, which sits in the same source folder as the route photos. The source is blue line art, RGB(53, 105, 172), on white. Every white pixel is keyed out, not only the ones reaching the image border, so the holes inside the molecule's nodes and the gap inside the compass ring go transparent too and the mark sits correctly on any background. The anti-aliased edges have the white unmixed out of them so no pale fringe survives.

Rendered at full opacity, 48px tall and 28px below 480px wide. The mobile size is set by width, not height: the mark is about 1.94:1, and anything wider than roughly 56px pushes "Excipient Sourcing Navigator" from two wrapped lines to three, which overflows the fixed 68px header. An earlier version of the mark was a solid blue badge and carried `opacity: 0.87` to stop it competing with the tool name; line art on a transparent background does not need that, and the same value just washes the strokes out.

## Route images (stage 2)

The seven route-of-administration cards use photos from `ea-work/data-for-daily-tasks/Routes of Administration - Images/`. Every source photo puts its subject on the same flat lavender backdrop, RGB(196, 206, 255), which `build-route-images.py` keys out so the subject sits directly on the card's blue.

```bash
python3 build-route-images.py    # writes assets/routes/*.webp
```

- Only backdrop connected to the image border is removed, so colours inside the subject that happen to match it (the pale blue capsule in Oral) stay opaque.
- Partly transparent edge pixels have the backdrop unmixed out of them, so no lavender fringe survives against the blue.
- The left edge of each image is ramped to zero alpha across `FADE_W` (22% of its width). Cards anchor the photo to their right edge, so without this the photo's left edge lands mid-card and shows as a hard vertical seam against the blue. The ramp is baked into the file, so it holds at any card width.
- Output is WebP, not PNG: these are photos with an alpha channel, where PNG is badly inefficient. The seven images are 3.1 MB as PNG and 189 KB as WebP.
- Adding or replacing a route image means dropping the file in the source folder and adding it to `FILES` in the script, then adding the route to `ROUTE_IMAGES` in `index.html`. A route with no image renders as a plain blue card.
- The lead route gets a full-width hero card and the other six fall into two rows of three. That is the `i === 0` case in `renderRoutes`, so it always follows whichever route the structure file lists first. Today that is Oral, which carries 261 of the 690 route/category slots. This only works because routes are ordered by relevance; sorting them alphabetically would put Oral fifth and leave a hole in the row above the hero.

## Behavior notes
- **Alphabetical from stage 3 down.** Categories, excipients, suppliers, and products are all sorted by `build-data.py`, so the JSON files match what the screen shows and nothing sorts at render time. The sort key is case-insensitive and accent-folded, so `Südzucker AG` files under S-u-d rather than after every z. Two deliberate exceptions:
  - **Stage 2 routes are ordered by relevance, not by name.** They keep the order of the H1 headings in `excipients-landscape-structure-v2.md`, currently Oral, Injectable, Inhalation / Pulmonary, Nasal, Topical, Ocular, Rectal & Vaginal. Reorder those headings to change it.
  - **Stage 6 keeps the primary-before-minor split**, with the sort running inside each of the two groups.
- **The two JSON files are fetched with `cache: 'no-cache'`.** They are regenerated whenever the source data changes and are served without a `Cache-Control` header, so a browser is otherwise free to keep a stale copy and quietly show an old landscape. This forces a revalidation on every load: unchanged data comes back as a 304 and costs nothing, changed data always arrives. Without it, a data rebuild is invisible to anyone who visited before.
- **Breadcrumb**: `Home` is the landing screen and is clickable from every one of stages 2 to 6. `Routes` is the route list. Both sit ahead of the chosen route, category, excipient, and supplier, so no single label ever stands for two different screens. Deepest path is `Home / Routes / Oral / Fillers & Diluents / Microcrystalline Cellulose (MCC) / Asahi Kasei`, which fits one line at 980px and wraps to two on a phone.
- **Stage 6 is an exact lookup.** Products are filed under an excipient in the source tree, so every product shown genuinely belongs to that excipient. The old keyword matcher in `index.html` is gone.
- **Product ordering**: products where the excipient is the substance or a primary component (tags 1, 2, 3) come first under a "Based on X" heading, then minor and derived ones (tags 4, 5, 6) under "X as a minor or derived component". When only one group exists, a single heading is used and the split is skipped.
- **Excipients with no supplier** (18 of 392, e.g. Water for Injection, the propellants) show a "currently unavailable" note instead of supplier buttons.
- **Suppliers with no portal page** (16 of 55, e.g. Merck KGaA, ABITEC, Omya) are still shown; they just render without the Supplier Page button.
- **Grouped grade variants** (37 products such as Cavamax W6 / W7 / W8) carry several shop links. Those cards are static and each variant gets its own link chip; single-link products stay fully clickable cards.
- **Excluded from the build**: the tree's `Unclassified` section and any `Unknown Supplier` section. `Ideal Cures` and `Budenheim` were removed at source.
- **Supplier name aliases**: `ShinEtsu` maps to `Shin-Etsu` and `Sudzucker` to `Südzucker AG`, handled in `build-data.py` so the source files stay untouched. The portal URL lookup canonicalizes both sides.
- Supplier page URLs live on the data (the `link` field), not in `index.html`. The in-page `SUPPLIER_URLS` map is intentionally empty and kept only as an optional override.
